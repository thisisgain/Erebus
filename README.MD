# GAIN Origin Theme

A modern WordPress block theme skeleton for 2026 built on:
- **Timber 2.x / Twig** for all block rendering
- **ACF** for structured field data extending block attributes
- **Block API v3** with full `block.json` declarations
- **Webpack** build pipeline with SCSS, JS, manifest-based cache busting
- **theme.json Schema v3** with a fully documented, brand-locked configuration

---

## Requirements

- PHP 8.4+
- WordPress 7+
- Node.js 22+ / npm 10+
- Composer 2+
- ACF Pro (recommended) or ACF Free

---

## Setup

```bash
# 1. Install PHP dependencies (Timber)
composer install

# 2. Install Node dependencies
yarn install

# 3. Development build (watch mode)
yarn watch

# 4. Production build (hashed filenames + minification)
yarn build:prod
```

Activate the theme in WordPress. WordPress will read `theme.json` automatically.

## Build Pipeline

### How it works

Webpack compiles two categories of assets:

**1. Global assets** (enqueued via WordPress `wp_enqueue_*`)

| Source | Output | Hook |
|--------|--------|------|
| `assets/scss/main.scss` | `public/css/style.[hash].css` | `wp_enqueue_scripts` |
| `assets/js/main.js` | `public/js/main.[hash].js` | `wp_enqueue_scripts` |
| `assets/scss/editor.scss` | `public/css/editor-style.[hash].css` | `enqueue_block_editor_assets` + `add_editor_style()` |
| `assets/js/editor.js` | `public/js/editor.[hash].js` | `enqueue_block_editor_assets` |

**2. Block assets** (enqueued automatically by WordPress via `block.json`)

| Source | Output | Registered via |
|--------|--------|----------------|
| `blocks/{name}/src/index.js` | `blocks/{name}/build/index.js` | `block.json editorScript` |
| `blocks/{name}/src/style.scss` | `blocks/{name}/build/style.css` | `block.json style` |
| `blocks/{name}/src/editor.scss` | `blocks/{name}/build/editor-style.css` | `block.json editorStyle` |

### Manifest & cache busting

In production (`npm run build`), all global assets get a content hash in their filename:
```
public/css/style.abc12345.css
public/js/main.def67890.js
```

`public/manifest.json` maps logical names → hashed names:
```json
{
  "css/style.css": "css/style.abc12345.css",
  "js/main.js": "js/main.def67890.js"
}
```

`inc/assets.php` reads this manifest at runtime to enqueue the correct URL. PHP caches the manifest in a static variable so it's only read once per request.

Block assets use no hashing — WordPress handles block asset versioning via `block.json version`.

## Adding a New Block

```bash
# 1. Create the block directory structure
mkdir -p blocks/my-block/{src,build,views}

# 2. Create block.json (copy from blocks/hero/block.json and modify)
# 3. Create src/index.js, src/edit.js, src/style.scss
# 4. Create views/render.twig
# 5. (Optional) Create acf-fields.php for ACF field group

# Webpack auto-discovers new blocks via glob pattern in webpack.config.js.
# PHP auto-registers new blocks via glob in inc/blocks.php.
# No manual registration required.
```

## Theme.json Brand Locking

The `theme.json` is configured for **maximum brand consistency**:

| Setting | Value | Effect |
|---------|-------|--------|
| `color.custom` | `false` | Editors cannot enter arbitrary hex values |
| `color.defaultPalette` | `false` | WordPress default palette hidden |
| `typography.customFontSize` | `false` | Editors locked to the defined type scale |
| `typography.defaultFontSizes` | `false` | WordPress default sizes hidden |
| `spacing.customSpacingSize` | `false` | Editors locked to the defined spacing scale |
| `appearanceTools` | `false` | No global override of individual false settings |

To allow more freedom in specific blocks, override per-block in `theme.json styles.blocks` or use `supports` in `block.json`.

## Timber & Twig

### Block rendering flow

1. WordPress calls `register_block_type()` with a `render_callback` (set in `inc/blocks.php`)
2. The callback calls `render_block_with_timber($block_name, $attributes, $content, $block)`
3. Timber compiles `blocks/{name}/views/render.twig` with:
   - `attributes` — block attribute values
   - `content` — InnerBlocks HTML
   - `block` — WP_Block instance
   - `fields` — ACF field values (if ACF active)
   - All global context (menus, site, options, etc.)

### ACF + Timber pattern

The recommended pattern for ACF integration:

```twig
{# In render.twig: #}
{% set heading = attributes.useAcfFields and fields.hero_heading
    ? fields.hero_heading
    : attributes.heading %}
```

This lets editors choose between inline editing (block attributes) and structured data (ACF fields) per-page, with the block attribute as the default fallback.

## Best Practice Notes

### block.json

- **Never change `name` after deployment** — it breaks all saved instances. Create a new block + transform instead.
- Set `"html": false` on all brand-locked blocks to prevent raw HTML editing.
- Set `"className": false` if you don't want editors adding arbitrary CSS classes.
- Use `"parent"` to restrict child blocks (e.g. Card inside CardGrid only). This hides them from the global inserter.
- Use `"ancestor"` instead of `"parent"` when the block can be nested at variable depths.
- The `"example"` field is important for a professional inserter experience — always provide realistic preview data.
- `"inserter": false` (in supports) is for blocks that should only be created programmatically or via transforms, not manually inserted.

### theme.json

- Use `var(--wp--preset--*)` everywhere in styles — never hardcode hex values. This ensures theme.json values cascade correctly.
- `appearanceTools: true` will override many `false` settings below it. Keep `false` for brand-locked themes.
- Block-level setting overrides in `styles.blocks` are the most surgical tool — use them to give specific blocks a stripped-back palette.
- CSS custom properties from `settings.custom` can be referenced via `var(--wp--custom--category--key)` anywhere in your CSS.

### Performance

- Block assets (`editorScript`, `style`, `editorStyle`) are **only enqueued when the block is used on the page** — a major performance advantage over global enqueues.
- Global assets in `public/` are always loaded. Keep `main.scss`/`main.js` lean — put heavy styles in block-specific files.
- Use `viewScriptModule` (not `script`) for Interactivity API blocks. The Interactivity API handles its own loading optimisation.
- Register only the image sizes your design actually uses (`inc/theme-setup.php`). WordPress generates all registered sizes for every upload.

### ACF

- Set `show_in_rest: true` on meta fields only if you need Gutenberg sidebar access or REST API access.
- ACF options pages are ideal for header/footer/global settings that editors need to control without touching template files.

### Accessibility

- Always use `get_block_wrapper_attributes()` in `render.php` (or pass wrapper attrs through Twig). This outputs alignment classes, colour classes, and spacing styles generated by WordPress from supports.
- Keep `color.enableContrastChecker: true` in block supports — this gives editors a real-time WCAG contrast warning.
- Use semantic HTML elements (`<header>`, `<main>`, `<nav>`, `<article>`, `<section>`) in Twig templates and template parts.
- The `anchor` support adds `id` attributes enabling in-page links — enable it on section-level blocks.
